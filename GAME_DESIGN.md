Single source of truth for game rules, data and build order. `AGENTS.md` (generated by IWSDK) owns framework rules. This file owns game rules. If they conflict on framework behaviour, AGENTS.md wins.

## 1. Competition target
Meta VR Start Developer Competition 2026. Tracks: Gaming, New Experience (started Sep 24, 2026). Awards to win: **Best First Five Minutes** and **Boldest Original Concept**.

Design tests every feature must pass:
- **Airplane seat test:** every interaction works inside a ~0.6 m (2 ft) radius, seated.
- **Bus stop test:** a complete, satisfying moment in under ~10 minutes. Fast cold start, clean pause/resume.
- **Take-it-away test:** no third-party service. Everything is built here.
- Hands-first: **no controllers required**. Hand tracking is the primary input. Controllers and desktop mouse/keyboard are fallbacks for testing only.

## 1a. Target devices and tools
- **Target devices: Meta Quest 1, Quest 2 and Quest 3** (standalone, Quest Browser, WebXR). Design for the weakest device (Quest 1) so the others run well too. Use **VR mode only**; passthrough and scene understanding are not needed.
- Quest 1 runs at 72 Hz, so the frame target is **72 fps (about 13.9 ms per frame)**. Quest 2 and 3 can reach higher refresh rates, but never depend on them.
- Hand tracking is requested as an optional XR feature (not required), so the session still starts on any device. Hand tracking is less steady on Quest 1, so use generous grab and snap tolerances, bigger targets, and always keep the fallbacks (off-hand pinch to fire, controller or desktop mouse for testing).
- Quest 1 is an older device and may lag behind in Quest Browser and WebXR support. Verify every feature on the lowest device you can access, and tell me what you could not test.
- **Quality tiers:** `low` (Quest 1), `medium` (Quest 2), `high` (Quest 3). Pick the starting tier from the device or measured frame time, and step down automatically if frames run long.
- **Environment:** the IDE is Google AI Studio / Antigravity with the VS Code terminal. If the agent cannot run terminal commands or the IWSDK CLI and MCP tools, it must say so and give me the exact commands to run, then I paste the output back.
- **Flat preview is not proof.** A normal browser tab or an AI Studio preview runs the page with mouse and keyboard and never starts a VR session, so it can look perfect while hands, controllers, grabbing and head position are broken. The only valid test of this game is an **XR session**: press **Enter XR** in the IWSDK emulator (Quest 3 profile by default, check the other devices offered) or run on a real headset. The AI Studio preview can be used for a quick visual check only. Also confirm the preview is the same IWSDK project and not a separate web app.
- **IWSDK Studio (Scene Editor):** open it from the managed browser window (the Runtime/Editor toggle after `npm run dev`). Use it to place and inspect objects and edit component values. Use code for behaviour. Remember the editor does not run systems, so confirm system-driven behaviour in Runtime. Open the editor at the start of every scene step and check `scene_get_state`.

## 2. Concept
You are a master gunsmith. Build guns from modular parts, **weld** them, test them at a range, earn money and XP, unlock skins, and fill your safe with a collection of 6+ guns.

**Signature mechanic: the Weld Forge.** Trace a glowing seam with a torch at the right speed. Weld quality (Weak / Solid / Perfect) changes the gun's accuracy, durability and sell value. This is the "only works in VR" hook.

## 3. Tech and project rules
- Fresh project from `npm create @iwsdk@latest`. Keep the scaffold. Do not convert to React, Next.js, Vue or a plain Three.js app. This is a WebXR game, not a website: no DOM landing pages or navbars; in-headset UI uses IWSDK spatial UI.
- IWSDK (WebXR), TypeScript, VR mode, hand tracking, `grabbing: true`, `locomotion: false`.
- Physics (Havok) only where it pays off: loose parts falling on the bench. Bullets use simple ballistics, not physics bodies.
- Layout: `iwsdk.config.json` (authority), `public/scenes/main.iwsdk.scene.json` (composition only, manifest IDs), `src/assets.ts` (`defineAssets`), `src/components.ts` (`defineComponents`), `src/scene-assets/*.scene-asset.ts` (procedural models), `src/systems/*` (behaviour), `src/data/*` (all game data).
- Models: procedural low-poly first (placeholders). Later swap important items for GLB by keeping the same asset ID. GLB rules: meters, Y-up, origin at the attach point, one part per file, socket nodes named `socket_barrel`, `socket_mag`, etc.
- All numbers (stats, prices, XP, tiers, orders) live in `src/data/`, never hard-coded in systems.

## 4. Interaction map (use everything IWSDK offers)
| Player intent | Gesture | IWSDK feature |
|---|---|---|
| Pinch: pick small parts, tools, tweak dials | Thumb + index | `Interactable` + `OneHandGrabbable` (small items) |
| Hold / grip: carry a gun or large part | Full-hand grab | `OneHandGrabbable` with a defined grip anchor per gun |
| Two-hand: steady a long gun, aim | Both hands | `TwoHandsGrabbable` (disable scale), plus custom off-hand steadiness |
| Move: pull far items in, return them | Ray + pinch | `DistanceGrabbable` (`MoveTowardsTarget`), with return-to-origin |
| Press: buttons, shop, safe lever, "?" help | Finger poke | `PokeInteractable` |
| Select: menus, skin picker, cards | Pinch or ray | `RayInteractable` + spatial UI panels (`.uikitml`) |
| Fire | Index-curl on the holding hand; fallback: off-hand pinch; desktop: mouse click | Custom hand-joint system |
| Rotate: spin gun to inspect | Grab and rotate | `OneHandGrabbable` rotate on |

**One input path rule:** every interaction goes through IWSDK interactables and pointers (`Interactable`, `RayInteractable`, `PokeInteractable`, grab components) so hands, controllers, XR rays and desktop mouse (`canvasPointerEvents`) all work through the same code. No mouse-only click handlers on the canvas, and no separate "flat version" logic.

Agent must verify with the IWSDK reference tools which hand gesture the grab pointer uses, and record the result here under "Verified interaction notes". Hand input quality varies by device (Quest 1 lowest, Quest 3 best), so use forgiving tolerances and test the weld and snap mechanics on the lowest device available. Hover and pressed states must always give visual (outline or glow) and audio feedback.

## 5. Reach rule (resolves bench size vs seat test)
The bench is visually large (about 1.6 m wide), but **everything the player must touch lives in a 0.6 m arc**. Far items (wall rack, back shelf, safe) are brought in with `DistanceGrabbable`. The shop is a pinch-swipeable card carousel, not a far shelf. Anything dropped or out of reach returns to its bin automatically.

## 6. Data model (draft; keep in `src/data/`)
Part: `id, name, slot, rarity, price, unlockLevel, stats{damage, accuracy, fireRate, recoil, magSize, weight}, compatibleFrames[]`.
Slots: `barrel, magazine, stock, sight, grip, muzzle, underBarrel`.
Gun archetypes (6): Revolver, Compact Pistol, SMG, Hunting Rifle, Pump Shotgun, Sniper Rifle. Stretch: Plasma Rail Gun.
Starter content (20+ items): 3 barrels, 3 magazines, 3 stocks, 3 sights (iron, red dot, scope), 2 grips, suppressor, muzzle brake, laser, foregrip. Tools: torch, screwdriver, wrench, hammer, pliers, oil can, vise, goggles.
Weld quality multiplier: Weak 0.85, Solid 1.0, Perfect 1.15 on accuracy and durability.
Skin: `id, name, rarity, unlockLevel, price, materialParams`. Skins are cosmetic material swaps applied at a paint station.
Save (localStorage, wrapped in try/catch): money, XP, level, unlocked parts and skins, safe contents, tutorial progress.

## 7. Systems
1. **Calibration:** both palms flat on the surface for 4-5 s. Two rings under the palms fill, expand, merge, fade. Lifting hands early shrinks them back. The bench then builds in.
2. **Parts and snapping:** slots show faint sockets. Compatible part nearby: green pulse and click. Incompatible: red pulse, no attach. Stat card updates live. While attached, remove the physics body.
3. **Weld Forge:** seam is a list of points. Progress rises when torch tip is near the seam and moving within a speed band. Too fast = Weak, too slow = overheat (burn), steady = Perfect. Pooled sparks, heat glow cooling white, orange, dark, bead trail.
4. **Disassembly and repair:** gun in the vise, pull parts off (screwdriver hold, hammer tap for welds). Durability, rust or cracks, repair station with progress ring.
5. **Range:** hold the gun, aim with hand direction. Recoil kick, bullet drop, spread from barrel and sight, tracer and muzzle flash. Targets: static, sliding, popup. Pay for accuracy, streaks, distance.
6. **Economy and progression:** coins fly out on payout. XP from builds, welds, repairs, hits. Levels unlock parts, guns, skins, order types. First gun is fast. Full 6-gun collection takes about 30-45 minutes.
7. **Orders:** blueprint requests like "accuracy 70+, mag 12+". Bonus cash and reputation.
8. **Safe:** drop a gun in, the door closes, miniature collection rack with stats. Collection counter.
9. **Guide cards:** floating card with icon and a line under 8 words, near the relevant object. Hides after first success. A "?" pad brings any card back. No text walls.
10. **Pause/resume:** pause on `visibilityState` change or lost hands, resume exactly where left.

## 8. First five minutes (judged)
- 0:00-0:20 calibration and bench build-in.
- 0:20-2:00 one guided pistol: glowing sockets, snap, first weld.
- 2:00-4:00 first shots at the range, first payout.
- 4:00-5:00 buy a part, see stats improve, receive the first order.
No instruction screens. Teach by glow, motion and sound.

## 9. Art, audio, performance
- Warm stylized low-poly workshop: pegboard, tool wall, lamp, safe, framed blueprint, shelves. Few materials, merged by material, static geometry frozen.
- Sound on every snap, weld, shot, coin, level-up (procedural Web Audio is fine). Visual feedback on every interactable.
- Budget: **72 fps minimum on every device (Quest 1 is the floor)**. Starting targets (my estimates, not from the reference repos; measure and adjust):
  | Tier | Device | Triangles | Draw calls | Notes |
  |---|---|---|---|---|
  | low | Quest 1 | ~60-80k | ~80-100 | no post-processing or bloom, no real-time shadows (blob or baked), textures 512-1024 px, fewer particles |
  | medium | Quest 2 | ~100-120k | ~120 | simple shadows for key objects, light effects |
  | high | Quest 3 | ~150k | ~150 | richer effects, more particles |
- No allocation in `update()`. Pool sparks, tracers, coins, bullet holes.
- Quality tiers are required (see 1a): detect the device, start on a safe tier, and step down automatically if frames run long. Use simple materials, merged static meshes, few lights.

## 11. Testing and definition of done
**Definition of "working":** it works in an active XR session (emulator or headset), not just in the flat preview. Every interaction claim needs proof from `npx @iwsdk/cli xr status` / `xr_get_session_status` plus a screenshot or log taken during the session.

**XR interaction debug checklist (run in this order when something cannot be grabbed, poked or selected):**
1. Did you press Enter XR? Is `xr_get_session_status` reporting an active session?
2. Is `grabbing: true` set in `iwsdk.config.json` (and the needed XR features such as `handTracking`)?
3. Does the entity have `Interactable` plus the right component (`OneHandGrabbable`, `TwoHandsGrabbable`, `DistanceGrabbable`, `RayInteractable`, `PokeInteractable`)? Check with `ecs_find_entities`.
4. Does it have real geometry the pointer can hit (a mesh or collider of sensible size)? Not hidden, not scaled to zero, not behind another surface.
5. Is it within reach (0.6 m seated) and positioned relative to the player origin?
6. Is the emulator in controller mode or hand mode, and does that match the test? Use the emulator panel to move and press.
7. Is the system registered, with no startup errors? Run typecheck and read the console (count only, no level filter).
8. Is the code using a mouse-only handler? Replace it with IWSDK pointer components.
- `npm run typecheck`, console clean, `ecs_find_entities` confirms expected entities, runtime screenshot per step.
- A scripted smoke test that plays the first five minutes in the emulator.
- Test on a real Quest early (same-Wi-Fi network URL from `npx @iwsdk/cli dev status`). Test the lowest tier on a Quest 1 or 2 if available, and confirm 72 fps. Check which headset devices the IWSDK emulator offers in `dev.emulator.device` and test the lowest one too.
- Check hand-tracking loss, pause and resume on each device you have.
- Debug hooks only with `?debug`.
- Record a 60-second gameplay video of the first five minutes.
- Commit to git after every working step.
